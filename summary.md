# Production Email Webhook Environment Setup

`EMAIL_WEBHOOK_ENDPOINT_TOKEN` and `EMAIL_WEBHOOK_SIGNING_SECRET` come from different places.

## `EMAIL_WEBHOOK_ENDPOINT_TOKEN`

This token is generated by the project owner; it does not come from Resend. A secure token has already been generated and saved in `apps/admin/.env.local`.

Copy the value after:

```env
EMAIL_WEBHOOK_ENDPOINT_TOKEN=
```

Keep this value private and do not commit it to Git.

## `EMAIL_WEBHOOK_SIGNING_SECRET`

Get this value from Resend:

1. Open the [Resend Webhooks dashboard](https://resend.com/webhooks).
2. Click **Add Webhook**.
3. Enter the following endpoint URL, replacing `YOUR_ENDPOINT_TOKEN` with the value from `apps/admin/.env.local`:

   ```text
   https://admin.gologs.com.ng/api/webhooks/v1/email/YOUR_ENDPOINT_TOKEN
   ```

4. Select these events:

   ```text
   email.sent
   email.delivered
   email.delivery_delayed
   email.bounced
   email.complained
   email.opened
   email.clicked
   ```

5. Create the webhook.
6. Open the webhook details and copy its **Signing Secret**. It should start with `whsec_`.
7. Replace the existing value in `apps/admin/.env.local`:

   ```env
   EMAIL_WEBHOOK_SIGNING_SECRET=whsec_your_real_secret_here
   ```

## Add the values to Vercel

Add both complete variables to the Vercel project:

```env
EMAIL_WEBHOOK_SIGNING_SECRET=whsec_your_real_secret_here
EMAIL_WEBHOOK_ENDPOINT_TOKEN=your_generated_token
```

Apply them to **Production**, save the changes, and redeploy. Environment-variable changes only apply to new deployments. Keep both values private.

Reference: [Resend webhook verification](https://resend.com/docs/webhooks/verify-webhooks-requests).

## 2026-09-16 — Email webhook endpoint-token clarification

The value for `EMAIL_WEBHOOK_ENDPOINT_TOKEN` is only the final path segment after `/api/webhooks/v1/email/`; it must not include the domain or the rest of the URL.

The complete Resend webhook URL uses this format:

```text
https://admin.gologs.com.ng/api/webhooks/v1/email/<EMAIL_WEBHOOK_ENDPOINT_TOKEN>
```

Because the current token was pasted into chat, rotate it before production launch: generate a new random token, update `EMAIL_WEBHOOK_ENDPOINT_TOKEN` in `apps/admin/.env.local` and Vercel, update the Resend webhook endpoint URL with the new token, and redeploy the Vercel production deployment. Do not store the real token in this tracked summary.

## 2026-09-16 — Production OTP 503 and CSP `eval` investigation

### Confirmed production failure

The live login page was inspected directly. It returned HTTP 200 but rendered the message `Admin authentication is not configured for this environment.` A harmless OTP request using a deliberately unauthorized diagnostic address returned HTTP 503. An unauthorized address should return HTTP 403 after the allowlist lookup, so the 503 proves the live deployment fails before email delivery because its complete environment validation or Supabase admin initialization is unavailable.

The local credentials were checked without printing their values:

- `admin_emails` is reachable through the configured Supabase secret key.
- `otp_codes` is reachable through the configured Supabase secret key.
- The Resend API key returns HTTP 200.
- The `gologs.com.ng` sending domain is verified in Resend.

Therefore, the provider credentials stored locally are healthy. The active Vercel deployment does not yet contain or use the same complete production environment. Vercel environment changes apply only to a new deployment.

After redeployment, load `/login`. The `Admin authentication is not configured` warning must be gone. Then request an OTP with an allowlisted administrator email.

### CSP cause and code fix

The CSP warning was independent of the 503. The client-side login form imported `OTP_RESEND_SECONDS` from the server-only `lib/auth/otp.ts` module. That transitively bundled the server environment validator and Zod into browser JavaScript. Zod's generated validator uses the `Function` constructor, which the production `script-src` policy correctly blocked.

The constant now lives in the browser-safe `src/lib/auth/constants.ts` module, and the login form imports it from there. The production CSP remains strict; `'unsafe-eval'` was not added. The rebuilt static browser bundles no longer contain the Zod dynamic compiler.

Production diagnostics were also improved:

- Invalid environment validation now logs the failing variable names/messages server-side without logging values.
- Resend failures now log the HTTP status and safe provider error message while the browser continues receiving a generic error.

Verification completed successfully:

- ESLint passed with zero warnings.
- TypeScript passed.
- All 9 automated tests passed.
- The optimized Next.js production build passed.
- The rebuilt client bundle contains no Zod dynamic compiler.

References: [Next.js CSP guidance](https://nextjs.org/docs/15/app/guides/content-security-policy), [Vercel environment variables](https://vercel.com/docs/environment-variables), and [Supabase observability](https://supabase.com/docs/guides/observability).

## 2026-09-16 — Safe Vercel fresh-deployment procedure

Do not delete the entire Vercel project as a first troubleshooting step. Deleting the project would also remove its custom-domain attachment, environment-variable configuration, deployment history, and other project settings. It is unnecessary for clearing a stale build.

Use this safe fresh-deployment procedure instead:

1. Open the existing Vercel project and go to **Settings → Environment Variables**.
2. Confirm all 11 variables listed in the production incident section are assigned to **Production**. Saving variables in Preview or Development does not make them available to the production deployment.
3. Go to **Settings → Build and Deployment** and confirm the Root Directory is `apps/admin`.
4. Open **Deployments**, select the newest deployment for Git commit `32c498c`, and choose **Redeploy**.
5. Disable/reject reuse of the previous build cache when prompted so Vercel performs a clean build.
6. Wait until the deployment status is **Ready** before testing the custom domain.
7. Verify that `https://admin.gologs.com.ng/login` no longer displays the environment-configuration warning, then request an OTP using an allowlisted administrator email.

Deleting only an obsolete deployment after the new deployment is healthy is optional; it does not repair environment variables. Do not delete the whole Vercel project unless intentionally rebuilding its domain, settings, and variables from scratch.
